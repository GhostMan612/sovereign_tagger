Channel count, sample rate, bit depth and sample/frame count were captured before and after every commit and are **identical in all eleven cases**; only whole-file size grows, because metadata is added. `AsfFileWriter.writeTag` takes two `RandomAccessFile`s and rewrites the whole file rather than patching in place, and `Mp4FileWriter` must relocate `mdat` as `moov` grows — those two were the real risk, and both preserve the audio bytes exactly.

What actually happens on commit: **metadata is APPENDED, audio is never rewritten.** WAV keeps `fmt` at offset 12 and `data` at offset 36 and gains a trailing `LIST`; AIFF gains an `ID3 ` chunk; MP3 gains an ID3v2 tag ahead of untouched frames; FLAC keeps its frames after a rewritten metadata block chain; MP4 keeps `mdat` and corrects `stco`; Ogg rewrites only the comment header and leaves audio pages; ASF rewrites the header objects and leaves the Data Object. That is a metadata edit, never a re-encode — the lossless law holds for the entire declared surface, not a sampled subset.

`dsf` was measured too, not merely argued. DSD cannot be produced by a PCM generator, so a spec-valid DSF was synthesised directly: a 28-byte `DSD ` header, a 52-byte `fmt ` chunk declaring DSD-raw / 2 channels / 2822400 Hz / 1 bit, and a `data` chunk holding 705600 bytes of deterministic pseudo-random 1-bit DSD. jaudiotagger read it correctly on the first attempt (`channels=2 rate=2822400 bits=1 samples=2822400`), committed cleanly, and left every one of those numbers identical afterwards. Its metadata lands differently from WAV/AIFF but equivalently harmlessly: there is no nested `ID3 ` chunk, instead the header's metadata pointer (`20:28`) is repointed at a **bare 206-byte ID3v2 tag appended after the DSD data**, so the `data` chunk stays at offset 80 with byte-identical contents. `DsfFileWriter.convert(AbstractID3v2Tag)` serialises only the tag; `DsdChunk.readChunk(ByteBuffer)` is a pure parse. Nothing in the DSF path can resample.

**Method caveats, so this is not over-trusted:**
- The first AIFF probe reported `CannotReadException: Not a valid header…Size:0` and it was **my generator's bug, not jaudiotagger's** — the SSND chunk size omitted its 8-byte `soundOffset`+`blockSize` header. A single failing probe is not evidence; the file was validated chunk-by-chunk before drawing any conclusion.
- My chunk-walking hasher then produced a *false* `payload=None` on the DSF, twice, for a different reason: **DSF declares chunk sizes as inclusive of the 12-byte chunk header, whereas RIFF/IFF are not** (and DSF's `data` chunk reports the payload length while `fmt ` reports the inclusive total). A parser that silently mis-walks looks exactly like a parser that found nothing. This is why the payload hash is cross-checked against the generator's own baseline rather than trusted on its own.
- Kotlin's `.tagOrCreateAndSetDefault` / `.isAndroid =` are **synthetic property access** onto `getTagOrCreateAndSetDefault()` / `setAndroid(boolean)`. The Java probe initially failed to compile against the same jar the app uses, which briefly looked like a version mismatch. It was not — `build.gradle` pins 3.0.1 and that is the only jar present.
- No test framework and no committed fixtures: the probe lived in `%TEMP%\opencode` and is not added to the repo, per the zero-test-suite directive. The recipe is recorded here so it can be re-run on demand.

**Net: the lossless law holds for every format in `writableExtensions`. No code change was required, and none was made.** The registry has no open defects.
